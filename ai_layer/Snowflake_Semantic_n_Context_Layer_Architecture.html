1. Executive Summary

Snowflake's position is that the Semantic View is the single, governed semantic layer that serves all downstream consumers — Cortex Agents, Cortex Analyst, custom AI agents, Tableau, Power BI, and any application consuming enterprise data. This eliminates the need to maintain parallel metadata layers across AI and BI workloads.

Define business logic once (in Semantic Views), enforce governance once (via Horizon), and consume everywhere — whether the consumer is a natural language agent, a SQL-based BI tool, or a custom application.

This document addresses each area of your inquiry with Snowflake's recommended architecture, maps your current custom agent components to Snowflake-native equivalents, and identifies where external components still add value.

4. Semantic Views: The Universal Context Layer

4.1 What is a Semantic View

A Semantic View is a Snowflake-native object that defines:

  • Tables and joins: which physical tables participate and how they relate
  • Dimensions: categorical columns for grouping/filtering
  • Measures: numeric columns for aggregation
  • Metrics: pre-defined business calculations with SQL expressions
  • Relationships: join paths between tables

It is NOT a SQL view — it is a metadata definition that Cortex Analyst uses to generate accurate SQL from natural language questions.

4.2 Why Semantic Views Are the Right Semantic Layer

RequirementHow Semantic Views Address It
Single definition of business metricsMetrics defined once in YAML, consumed by all channels
Governed accessInherits Horizon policies (masking, row access) on underlying tables
Multi-domain scalabilityOne Semantic View per domain (10-50 tables each), independently owned

BI consumptionTableau/Power BI query governed tables; metric definitions serve as catalog
Custom agent consumptionREST API: POST /api/v2/cortex/analyst/message with semantic_view parameter
VersioningSnowflake objects with DDL lifecycle (CREATE, ALTER, DROP)

4.3 Multi-Domain Routing Pattern

For enterprises with many data domains (500+ tables across 20+ business units):

Pattern: Each domain team owns their Semantic View independently. A SEMANTIC_MODEL_REGISTRY table catalogs all domains. MODEL_ROUTER_SEARCH (Cortex Search) indexes the registry. The Enterprise Agent uses the router to identify which domain can answer a question, then calls the appropriate analyst tool. This scales to any number of domains without a monolithic model.

5. Deep Dive: Architecture Components

5.1 Structured Data Grounding (Cortex Analyst + Semantic Views)

Problem: AI agents need to answer questions about structured enterprise data with SQL accuracy.

Solution: Cortex Analyst converts natural language to SQL using Semantic View definitions as context.

Quality Controls: Verified Queries (VQRs) for pre-validated question-SQL pairs. Metric expressions use exact SQL, not LLM-interpreted. Automated evaluation of SQL generation accuracy.

5.2 Unstructured Data Grounding (Cortex Search / RAG)

Problem: Agents need to answer questions using unstructured documents and free-text data.

Solution: Cortex Search provides hybrid retrieval (vector + keyword + reranker) over text data in Snowflake tables.

  • Hybrid search: dense vector similarity + BM25 keyword + cross-encoder reranker
  • Auto-embedding: snowflake-arctic-embed — no external pipeline
  • Incremental refresh: TARGET_LAG controls freshness
  • Attribute columns: structured metadata returned with search results

7. Target-State Architecture

The 4-layer architecture diagram above (Section 2.1) represents the recommended target state. The key design principles:

  1. Semantic Views as the single source of truth for business metrics and relationships
  2. Cortex AI services as the intelligence layer — agents, analyst, search, complete
  3. Snowflake as the single data platform — structured, unstructured, streaming, metadata
  4. Horizon as the universal governance layer — policies follow data, not consumers

8. Recommended Next Steps

  1. Start with Semantic Views — define 2-3 domain Semantic Views over your highest-value datasets. This is the foundation for both AI and BI consumption.
  2. Deploy a Cortex Agent — create a single-domain agent with one cortex_analyst_text_to_sql tool pointing at a Semantic View. Test in CoWork.
  3. Add Cortex Search — index unstructured data for RAG. Add as a tool to the agent.
  4. Layer in Governance — apply Horizon tags and policies. Verify same governance applies regardless of access path.
  5. Scale to multi-domain — more Semantic Views, domain registry, Enterprise Agent with routing.
  6. Evaluate custom agent needs — if Cortex Agents don't cover your orchestration requirements, use your existing framework but replace the data grounding layer with Snowflake-native services.
  7. Build observability — start with query history + event tables. Add external agent observability only if needed.
